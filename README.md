# tomato-intepretato

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
```

Первая конфигурация скачивает nlohmann/json.

```sh
build/bin/tomato-intepretato -i program.json < input.txt
build/bin/tomato-intepretato -c program.json > program.sm
build/bin/tomato-intepretato -x program.sm < input.txt
build/bin/tomato-intepretato -m program.json < input.txt
build/bin/tomato-intepretato -k program.json < input.txt
```

`-i` запускает AST-интерпретатор. `-c` компилирует AST в текст программы стековой машины. `-x` загружает и выполняет такую программу. `-m` компилирует и сразу выполняет. `-k` запускает AST-интерпретатор и стековую машину с одинаковым вводом и сравнивает stdout и успешность выполнения. При совпадении успешных запусков возвращается 0, при ошибке или расхождении — 1. Диагностика идёт в stderr.

Ровно один флаг режима обязателен; режима по умолчанию нет. Без флага или при выборе нескольких режимов программа завершается с кодом 2. Справка доступна без выбора режима.

Режимы также доступны по полным именам: `--interpret`, `--compile`, `--machine`, `--execute`, `--check`. Путь можно передать позиционно либо через `-p`/`--path`. Справка — `-h`/`--help`.

По умолчанию формат входа — JSON AST. Флаг `-s` / `--script` выбирает исходный текст; он дополняет обязательный флаг режима, например `-i -s` или `-c -s`. Если путь к JSON не указан, AST и данные для `read` можно подать последовательно в stdin. Для `-x` с вводом используйте отдельный файл программы.

| Команда | Действие |
| --- | --- |
| `CONST n` | Положить целое число на стек |
| `LD x` | Положить значение переменной на стек |
| `ST x` | Снять значение со стека и записать в переменную |
| `READ` | Прочитать целое число и положить на стек |
| `WRITE` | Снять значение и вывести с переводом строки |
| `BINOP op` | Снять правый и левый операнды, положить результат |
| `LABEL name` | Объявить метку |
| `JMP name` | Перейти на метку |
| `CJMP z, name` | Снять значение и перейти, если оно равно нулю |
| `CJMP nz, name` | Снять значение и перейти, если оно не равно нулю |
| `END` | Завершить выполнение |

Операторы: `+`, `-`, `*`, `/`, `%`, `==`, `!=`, `<`, `>`, `<=`, `>=`, `&&`, `!!`. Арифметика совпадает с AST-интерпретатором: целые 64-битные числа, деление к нулю, оба операнда логических операций вычисляются.

Выражение оставляет одно значение на стеке, инструкция языка сохраняет размер стека. Компилируются присваивания, read/write, skip, последовательности, if/elif/else, while, do-while и for с init/cond/step.

## Как связаны AST, компилятор и стековая машина

У программы есть два пути выполнения:

```text
JSON → JsonAstBuilder ─────────┐
                              ├→ AST → evaluate/execute → результат
Текст → Lexer → Parser ────────┘      ↘ compile → Program → StackMachine → результат
```

`JsonAstBuilder` из `lib/ast/ast_builders/json_builder/` разбирает представление дерева. Объекты `NumberExpr`, `VariableExpr`, `BinaryOpExpr`, `AssignStmt`, `ReadStmt`, `WriteStmt`, `WhileStmt` и остальные узлы находятся в `lib/ast/ast.h`. Последовательности JSON превращаются в списки инструкций AST (`AST` — это `vector<StmtNode>`).

AST-интерпретатор вызывает `execute` у инструкций и `evaluate` у выражений. Например, `WhileStmt::execute` сам проверяет условие и повторяет выполнение тела.

Компилятор из `lib/sm/compiler/` использует тот же AST. `main` строит AST через `JsonAstBuilder` либо `ScriptAstBuilder` и передаёт его выбранному исполнителю. `Compiler::compile` принимает готовое дерево, вызывает `compile` у каждого верхнеуровневого узла, добавляет `END` и возвращает `Program`. Методы `compile` рекурсивно обходят дерево и добавляют команды в `Program`. Они не вычисляют значения переменных и не выполняют цикл: тело цикла генерируется один раз, а повторение обеспечивают переходы.

`AssignStmt`, `ReadStmt` и `WriteStmt` — отдельные инструкции AST. Их `execute` изменяет переменную или выполняет ввод/вывод, а `compile` генерирует команды SM. Они не являются выражениями и не возвращают значение.

`Program` из `lib/sm/program/` хранит `vector<Instruction>`. У команды есть код операции и необходимые операнды: число, имя переменной, оператор или имя метки. `emit_*` добавляют команды, `new_label` выдаёт имена `L1`, `L2` и далее. `Program::print` сохраняет команды в текст, `Program::read` читает этот текст обратно. Здесь компиляция означает перевод AST в инструкции нашей виртуальной машины; процессорный машинный код не создаётся.

`StackMachine` из `lib/sm/machine/` выполняет `Program` без обращения к AST. Её состояние состоит из:

- `stack_` — стека промежуточных целочисленных значений;
- `variables_` — таблицы имён переменных и их значений;
- `ip` — индекса текущей команды в векторе программы;
- таблицы меток, которая сопоставляет имя метки индексу команды `LABEL`.

Перед запуском машина очищает стек и переменные, собирает метки, проверяет их дубликаты и наличие целей переходов. Обычно после команды `ip` увеличивается на один. Переход записывает в `ip` индекс нужного `LABEL`; сама команда `LABEL` ничего не делает, и выполнение продолжается за ней. `END` завершает запуск. Пустой стек при снятии значения, неизвестная переменная, неверный ввод и деление на ноль приводят к ошибке.

## Пример: цикл от 0 до 2

Рассмотрим программу:

```text
{
    i = 0;
    while (i < 3) {
        write(i);
        i = i + 1;
    }
}
```

Она выводит:

```text
0
1
2
```

Для запуска через JSON сохраним в `loop.json` следующее дерево. Массивы здесь обозначают последовательности инструкций; builder также принимает вложенные узлы `seq` с `left` и `right`.

```json
[
  {"assign": {"var": "i", "value": {"const": 0}}},
  {
    "while": {
      "cond": {
        "binop": "<",
        "left": {"var": "i"},
        "right": {"const": 3}
      },
      "body": [
        {"write": {"var": "i"}},
        {
          "assign": {
            "var": "i",
            "value": {
              "binop": "+",
              "left": {"var": "i"},
              "right": {"const": 1}
            }
          }
        }
      ]
    }
  }
]
```

В AST это две верхнеуровневые инструкции: `AssignStmt` для начального присваивания и `WhileStmt`. У цикла условие — `BinaryOpExpr` для `<`, а тело — список из `WriteStmt` и `AssignStmt`. Компиляция бинарного выражения сначала генерирует левый операнд, затем правый, затем `BINOP`.

### Сгенерированная программа

Команда:

```sh
build/bin/tomato-intepretato -c loop.json > loop.sm
```

Создаёт ровно такую последовательность из 16 команд:

```text
CONST 0
ST i
LABEL L1
LD i
CONST 3
BINOP <
CJMP z, L2
LD i
WRITE
LD i
CONST 1
BINOP +
ST i
JMP L1
LABEL L2
END
```

Первые две команды выполняют `i = 0`. `LABEL L1` отмечает начало проверки условия. `CJMP z, L2` выходит из цикла при ложном условии. Между ним и `JMP L1` находится тело: вывод `i` и увеличение `i`. `LABEL L2` отмечает конец цикла.

В `WhileStmt::compile` это общий шаблон: метка начала → условие → условный выход → тело → переход к началу → метка конца. В AST нет готовых номеров команд для переходов, поэтому компилятор использует имена меток, а машина разрешает их перед запуском.

### Выражения и инструкции

Выражение оставляет на стеке одно число. Присваивание, ввод и вывод — инструкции: они используют полученное число и не оставляют результата на стеке. Поэтому после каждой завершённой инструкции глубина стека сохраняется.

`i = 0;` компилируется в:

```text
CONST 0
ST i
```

`CONST 0` кладёт число на стек, а `ST i` снимает его и записывает в переменную. После присваивания стек снова пуст.

`read(i);` компилируется в:

```text
READ
ST i
```

`READ` читает число из входного потока и кладёт на стек, `ST i` переносит его в переменную.

`write(i);` компилируется в:

```text
LD i
WRITE
```

`LD i` загружает значение переменной, а `WRITE` снимает его и выводит. Сохранять копию числа не нужно: инструкция вывода не возвращает значение. Команд `DUP` и `POP` в машине нет. Использовать присваивание, read или write внутри выражения нельзя — например, `write(i = 0)` не входит в язык задания.

### Выполнение первой итерации

Ниже стек записан слева направо от дна к вершине. В начале стек пуст, переменная `i` ещё не определена.

| Команда | Стек после команды | Переменная `i` | Эффект |
| --- | --- | --- | --- |
| `CONST 0` | `[0]` | — | Положили начальное значение |
| `ST i` | `[]` | 0 | Записали значение в переменную |
| `LABEL L1` | `[]` | 0 | Начали проверку условия |
| `LD i` | `[0]` | 0 | Загрузили левый операнд |
| `CONST 3` | `[0, 3]` | 0 | Загрузили правый операнд |
| `BINOP <` | `[1]` | 0 | Вычислили `0 < 3` |
| `CJMP z, L2` | `[]` | 0 | Сняли 1, переход не выполнили |
| `LD i` | `[0]` | 0 | Загрузили аргумент вывода |
| `WRITE` | `[]` | 0 | Вывели `0` и перевод строки |
| `LD i` | `[0]` | 0 | Начали вычислять `i + 1` |
| `CONST 1` | `[0, 1]` | 0 | Положили второй операнд |
| `BINOP,kby +` | `[1]` | 0 | Получили новое значение |
| `ST i` | `[]` | 1 | Обновили переменную |
| `JMP L1` | `[]` | 1 | Вернулись к проверке условия |

Порядок снятия операндов важен: `BINOP` сначала снимает правый операнд, затем левый. Например, из `[0, 3]` получается именно `0 < 3`, а не `3 < 0`. Операция берётся из общих `ValueOps`, которыми пользуется и AST-интерпретатор.

### Следующие итерации и выход

| `i` перед проверкой | Результат `i < 3` | Действие | `i` после тела |
| --- | --- | --- | --- |
| 0 | 1 | Вывести 0, выполнить тело | 1 |
| 1 | 1 | Вывести 1, выполнить тело | 2 |
| 2 | 1 | Вывести 2, выполнить тело | 3 |
| 3 | 0 | Перейти к `L2`, затем выполнить `END` | 3 |

При последней проверке `BINOP <` кладёт на стек 0. `CJMP z, L2` снимает его и переносит выполнение к метке выхода. Тело больше не выполняется, поэтому число 3 не выводится. При завершении `i` равно 3, стек пуст.

Один и тот же сгенерированный участок тела выполняется трижды. 16 — число команд в программе, а не число выполненных шагов: часть команд исполняется повторно из-за переходов.

### Проверка совпадения

```sh
build/bin/tomato-intepretato -i loop.json
build/bin/tomato-intepretato -x loop.sm
build/bin/tomato-intepretato -k loop.json
```

Каждый запуск выводит `0`, `1`, `2` на отдельных строках. Последний дополнительно пишет в stderr:

```text
check: results agree
```

В режиме `-k` из одного JSON или исходного текста строятся два одинаковых AST: для интерпретатора и компилятора. Оба запуска получают отдельные потоки с одинаковыми входными данными. Затем сравниваются весь stdout и факт успешного завершения либо ошибки. Сообщения ошибок, конечные таблицы переменных и содержимое стека этот режим не сравнивает. Это проверка совпадения на конкретном запуске, а не доказательство эквивалентности для всех возможных входов.


## Что нужно объяснить на защите

В проекте два способа построения дерева: JSON → `JsonAstBuilder` → AST и текст → `ScriptAstBuilder` → Lexer → Parser → AST. Builder’ы создают одинаковые типы узлов, поэтому компилятору и интерпретатору не нужно знать формат входа. Общей фабрики и интерфейса `IAstBuilder` нет. JSON разбирает nlohmann/json, текст — небольшой лексер и парсер языка задания. Аргументы командной строки разбирает `ArgumentParser::ArgParser` из `lib/argparser.h`. В `main` объявлены путь, пять режимов, формат текста и справка.

Иерархия AST сохранена: `BaseExpr` задаёт `evaluate` и `compile`, `BaseStmt` — `execute` и `compile`. Инструкции не возвращают значение; выражения возвращают целое число. Неиспользуемые узлы строк, коллекций, пользовательских функций, return, break и continue удалены. В языке задания их нет. Бинарная операция хранится строкой (`+`, `<` и т. д.), поэтому отдельный набор токенов лексера не нужен.

Присваивание, read и write представлены узлами `AssignStmt`, `ReadStmt` и `WriteStmt`. Общей системы вызовов функций и таблицы встроенных функций нет. `ReadStmt` хранит имя переменной и ссылку на входной поток, `WriteStmt` — выражение и ссылку на выходной поток. Потоки передаются в `JsonAstBuilder` при построении AST, поэтому проверка может запустить программу дважды на одинаковых данных. `AssignStmt` хранит имя переменной и выражение правой части; проверять тип левой части через `dynamic_cast` не требуется.

Сборка состоит из одной библиотеки `tomato_core` и одного исполняемого файла. Файлы сгруппированы по назначению:

| Путь | Что находится внутри |
| --- | --- |
| `bin/main.cpp` | Выбор режима, чтение JSON, запуск и сравнение |
| `lib/ast/ast.h` | Узлы дерева с интерпретацией и компиляцией |
| `lib/ast/common/value.h` | Тип числа и общая реализация бинарных операций |
| `lib/ast/ast_builders/json_builder/` | Построение дерева из JSON |
| `lib/ast/ast_builders/script_builder/` | Построение AST из текста: лексер и парсер |
| `lib/interpreter/` | Последовательное выполнение инструкций AST |
| `lib/sm/compiler/` | Последовательная компиляция узлов AST |
| `lib/sm/program/` | Команды SM, печать и чтение программы |
| `lib/sm/machine/` | Стек, переменные, счётчик команд и исполнение |
| `lib/common/errors.h` | Ошибки и позиции команд |

При демонстрации достаточно пройти по примеру цикла выше: показать JSON, результат `-c`, объяснить переход назад к `L1` и выход через `L2`, затем запустить `-k`.

## Поддерживаемые формы JSON

Builder принимает следующие формы. `E` означает выражение, `S` — инструкцию или последовательность. Альтернативные названия полей не угадываются: используется один набор имён.

| Узел | Форма |
| --- | --- |
| Число | `{"const": 1}` |
| Переменная | `{"var": "x"}` |
| Бинарная операция | `{"binop": "+", "left": E, "right": E}` |
| Ввод | `{"read": "x"}` |
| Вывод | `{"write": E}` |
| Присваивание | `{"assign": {"var": "x", "value": E}}` |
| Составное присваивание | `{"assign": {"var": "x", "op": "+", "value": E}}` |
| Последовательность | `{"seq": {"left": S, "right": S}}` или массив инструкций |
| Условие | `{"if": {"cond": E, "then": S, "else": S}}`, else необязателен |
| while | `{"while": {"cond": E, "body": S}}` |
| do-while | `{"do": {"body": S, "cond": E}}` |
| for | `{"for": {"init": S, "cond": E, "step": S, "body": S}}` |
| skip | `{"skip": null}` |

`elif` представляется вложенным `if` в ветке `else`, как в примере задания. Для присваивания и циклов здесь зафиксирован формат проекта; его соответствие выгрузке эталона нужно проверить на реальных примерах этих узлов.


## Исходный текст вместо JSON

Текстовый builder поддерживает язык задания: блоки в фигурных скобках, read/write, присваивание и составное присваивание, skip, if/elif/else, while, do-while и for. Комментарии исходного языка: `--` до конца строки и `(* ... *)`. Выражения содержат целые неотрицательные константы, переменные, скобки и бинарные операции; отрицательное значение можно записать как `0 - 10`.

Сохранив исходный текст цикла из примера выше в `loop.is`, можно выполнить:

```sh
build/bin/tomato-intepretato -i -s loop.is
build/bin/tomato-intepretato -c -s loop.is > loop.sm
build/bin/tomato-intepretato -m -s loop.is
build/bin/tomato-intepretato -k -s loop.is
```

Режим `-x` читает готовые команды SM и с флагом `-s` не сочетается. Если текстовая программа использует read, передавай исходник отдельным файлом, а данные — через stdin: текстовый builder читает источник целиком. Разделять исходник и данные в одном stdin для текстового режима не предусмотрено.

Приоритеты операций от низшего к высшему: `!!`, `&&`, `== !=`, `< > <= >=`, `+ -`, `* / %`. Операторы одного уровня группируются слева направо. Скобки позволяют явно задать порядок.
